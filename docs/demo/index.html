**EC-5: `crit_multiplier_effective` at maximum**
`crit_multiplier_effective=3.25` (Hero System pre-computes: `1.75 base + 1.50 max bonus`). A crit on an ELITE target with base_damage=100: `floor(100 × hero_damage_bonus_multiplier × 3.25)` = `floor(100 × 1.50 × 3.25) = floor(487.5) = 487` (at default hero_damage_bonus_multiplier=1.50). This is the maximum output of Formula D2 for a given base_damage. Equipment Forge GDD must ensure no equipment combination can produce `crit_multiplier_effective > 3.25`. D&S does not re-clamp this value — it trusts Hero System pre-validation. Note: at max crit chance (80%) the expected DPS vs ELITE/BOSS (2.40× of base_damage) always exceeds expected DPS vs STANDARD (1.60× of base_damage) at any crit rate — the hero's tier bonus applies to crit and non-crit hits alike, so ELITE/BOSS are always the hero's superior DPS targets.

#### Armored Hit Effect (`archetype_tag = &"armored"`)

When a tower deals damage to an `armored` entity, the 50% mitigation must be visually distinguishable from an unmitigated hit. Players cannot make informed placement decisions near armored enemies if mitigated hits look identical to normal hits.

**Required visual (one of):**
- Metallic spark burst: 2–4 particles, silver/grey palette, at the hit point — distinct from the standard damage-flash white
- Shield flash highlight: silver-tinted sprite overlay, 2–3 frames duration, distinct from standard white damage flash

**Not required:** Modification to the floating damage number — the number already reflects the mitigated amount. The visual should communicate "this hit was reduced", not duplicate the number.

**Art/UX delegation:** Exact treatment (spark vs. flash) is delegated to Art Director and UX Designer. This requirement specifies the information need — armored mitigation must be visually distinguishable — not the execution.

**Hero damage is unaffected:** Hero hits on armored entities use no mitigation and therefore no armored-hit visual. The armored visual is tower-hit-only.

| Mode | Behavior |
    |------|----------|
    | `CLOSEST_TO_GOAL` | Furthest along path (default if no Focus) |
    | `SPAWN_ORDER` | Targets the enemy with the **lowest `entity_id`** currently in range and cone that is alive. `entity_id` is assigned sequentially at spawn — lower IDs = earlier spawns in the mission. Among valid candidates, the earliest-spawned living monster in range is always selected. This is fully deterministic from `_monster_cache` with no additional per-tower state. If the current lowest-id target dies or exits range, the tower immediately selects the next-lowest-id alive target in range on the next attack cycle. Resets naturally via cache — no per-wave list management required. **SPAWN_ORDER determinism dependency:** Entity IDs are only deterministic if the Monster System processes `monster_spawn_requested` synchronously (not deferred). If monster spawning is batched or deferred, `entity_id` assignment order may diverge from emission order, breaking SPAWN_ORDER stability. The Monster System must process `monster_spawn_requested` synchronously and assign `entity_id` at the moment of `monster_spawned` emission — this is a cross-system contract. **Cross-doc verification required:** Monster GDD must explicitly state that `entity_id` is assigned synchronously at spawn. ## tower.md Rule 15 — SPAWN_ORDER: lowest entity_id among valid candidates.
## Fully deterministic on its own; entity_id is a total order, so no
## separate tiebreaker chain is needed (Rule 15's own wording).
func _find_spawn_order_target(state: TowerMissionState) -> int:
	var best_id: int = -1
	for entity_id: int in _candidates_in_range(state):
		if best_id == -1 or entity_id < best_id:
			best_id = entity_id
	return best_id
